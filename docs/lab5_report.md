# Лабораторная работа №5

**по дисциплине «Конструирование программного обеспечения»**  
**Тема: Управление исходным кодом и отслеживание метрик**

## 1. Создание проекта в системе хостинга

Для хранения исходного кода выбран GitHub. Репозиторий предназначен для курсового проекта «Разработка web-приложения анализа цен на товары».

Приложение предназначено для сбора, хранения и анализа цен на товары в различных магазинах. Пользователь сможет управлять каталогом товаров, импортировать цены, просматривать историю изменения стоимости, сравнивать цены, визуализировать динамику и формировать отчёты.

Используемый технологический стек согласован с проектированием, выполненным в лабораторной работе №4:

| Компонент | Технологии |
|---|---|
| Клиентская часть | React, Vite, HTML5, CSS3 |
| Серверная часть | Java 21, Spring Boot |
| База данных | PostgreSQL |
| Доступ к данным | Spring Data JPA / Hibernate (при реализации доступа к БД) |
| Контроль версий | Git, GitHub |
| Автоматизация проверок | GitHub Actions |
| Таск-трекер | YouGile |

Репозиторий разделён на каталоги `frontend` и `backend`. Каталог `.github/workflows` содержит сценарии автоматизации, а `test-metrics` — скрипт сбора метрик и отчёт CI. Файл `.gitignore` исключает из системы контроля версий собранные файлы, временные каталоги, настройки IDE и локальные файлы с секретами.

## 2. Порядок управления исходным кодом

### 2.1. Фиксация изменений (Commit)

Для оформления сообщений коммитов применяется соглашение Conventional Commits. Сообщение имеет формат:

`type(scope): краткое описание изменения`

Основные типы:

- `feat` — добавление функциональности;
- `fix` — исправление ошибки;
- `docs` — изменение документации;
- `style` — изменения оформления кода без изменения логики;
- `refactor` — изменение структуры кода без добавления функций;
- `test` — добавление или изменение тестов;
- `build` — изменение сборки и зависимостей;
- `ci` — изменение CI/CD;
- `perf` — улучшение производительности;
- `chore` — прочие технические изменения.

Примеры корректных сообщений:

- `feat(catalog): add product list`
- `fix(prices): validate imported price`
- `test(analysis): cover average price calculation`
- `ci(actions): upload coverage report`
- `docs(readme): describe local setup`

Для автоматической проверки сообщений коммитов добавлен workflow `commit-check.yml`, использующий commitlint при отправке изменений в рабочие ветки и создании Pull Request. Дополнительно настроен локальный hook Husky `commit-msg`, который проверяет сообщение до создания коммита. Это позволяет выявлять сообщения, не соответствующие принятому формату.

### 2.2. Ветвление (Branching)

Для проекта используется упрощённая стратегия Git Flow. Назначение веток:

| Ветка | Назначение |
|---|---|
| `main` | Стабильная версия проекта, готовая к демонстрации и выпуску релиза |
| `develop` | Интеграция разработанных функций перед выпуском |
| `feature/<название>` | Разработка новой функции, например `feature/product-catalog` |
| `fix/<название>` | Исправление ошибки, например `fix/price-validation` |
| `release/<версия>` | Подготовка версии к выпуску и финальные проверки |

Новая функция разрабатывается в отдельной ветке `feature/...`, созданной от `develop`. После реализации создаётся Pull Request в `develop`. Исправления выполняются в ветках `fix/...`. При подготовке версии создаётся ветка `release/...`, после проверки изменения объединяются с `main`, версия помечается Git-тегом, а необходимые изменения возвращаются в `develop`.

### 2.3. Слияние изменений (Merging)

Слияние выполняется через Pull Request. Перед объединением изменений GitHub Actions проверяет стиль исходного кода, выполняет тесты, формирует отчёты о покрытии и запускает сборку. Изменения объединяются только после успешного прохождения обязательных проверок.

Для веток `main` и `develop` в настройках GitHub следует включить защиту: обязательный Pull Request, обязательное прохождение статусных проверок, запрет принудительной отправки (`force push`) и запрет удаления веток. Для `main` также рекомендуется требовать одобрение Pull Request, если работа ведётся с проверяющим или другими участниками.

Защитные правила настраиваются в GitHub вручную в разделе `Settings → Branches` (или `Settings → Rules → Rulesets`, в зависимости от доступного интерфейса). После первого запуска Actions необходимо выбрать фактические имена проверок `quality-build-metrics` и `commitlint` в списке обязательных status checks. Для GitHub Free возможности защиты веток зависят от видимости репозитория и доступного тарифа, поэтому для учебного репозитория следует проверить актуальные условия аккаунта или использовать публичный репозиторий.

### 2.4. Контроль качества исходного кода

Для клиентской части применяется ESLint. Он проверяет синтаксические и стилистические проблемы и помогает находить потенциальные ошибки JavaScript/React. Для серверной части используется компиляция Java в составе Maven-сборки и выполнение тестов. В стартовой заготовке есть модульный тест функции форматирования цены на frontend и интеграционный тест HTTP-эндпоинта `/api/health` через Spring Boot и MockMvc на backend. Результаты тестов формируются в JUnit XML, покрытие измеряется средствами Vitest и JaCoCo. Интеграционные тесты с PostgreSQL нужно расширить после реализации репозиториев и слоя доступа к данным.

Настройки проверок находятся в `frontend/eslint.config.js`, `frontend/package.json` и `backend/pom.xml`. Проверки вызываются в GitHub Actions при каждом push и Pull Request. При обнаружении ошибок соответствующий workflow завершается с ошибкой, поэтому такой код нельзя объединить в защищённую ветку при включённом требовании успешных проверок.

### 2.5. Создание релиза

Для нумерации версий используется схема SemVer: `MAJOR.MINOR.PATCH`, например `v1.0.0`. Тег создаётся на коммите, который соответствует версии, проверенной перед релизом.

Пример порядка выпуска:

1. Создать ветку `release/1.0.0` от `develop`.
2. Выполнить финальные проверки и обновить описание версии.
3. Создать Pull Request в `main` и дождаться успешного CI.
4. После слияния создать аннотированный тег `v1.0.0` и отправить его в GitHub.
5. На вкладке Releases создать релиз по тегу и указать список изменений.

Команды для создания тега:

```bash
git checkout main
git pull origin main
git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0
```

Создание GitHub Release выполняется на странице `Releases → Draft a new release` с выбором тега.

## 3. Автоматизация процессов с помощью GitHub Actions

В репозитории предусмотрен workflow `.github/workflows/ci.yml`. Он запускается при `push` в рабочие ветки, при Pull Request в `main` или `develop`, а также вручную.

Пайплайн выполняет следующие действия:

1. Получает исходный код и историю Git.
2. Настраивает окружения Node.js 22 и Java 21.
3. Устанавливает зависимости frontend.
4. Запускает ESLint и сохраняет JSON-отчёт.
5. Запускает модульные тесты frontend с формированием отчёта о покрытии.
6. Выполняет Maven-проверки backend и формирует отчёт JaCoCo.
7. При успешном прохождении проверок собирает frontend и backend.
8. Автоматически рассчитывает метрики качества и процесса разработки.
9. Сохраняет сборки, отчёты тестов и метрик в GitHub Actions Artifacts.

Автоматическое развёртывание в отдельную тестовую среду не включено: в текущем описании проекта не определена конкретная площадка размещения, адрес окружения и необходимые секреты. Этот этап можно добавить после выбора среды развёртывания.

## 4. Сбор и анализ метрик

Метрики автоматически собираются скриптом `test-metrics/collect_metrics.py` в конце каждого запуска CI. Отчёты публикуются как артефакты запуска GitHub Actions. Поэтому результаты можно сохранять после завершения этапа разработки и сравнивать между последовательными этапами или релизами.

| № | Метрика | Способ расчёта / источник | Когда измеряется |
|---:|---|---|---|
| 1 | Количество ошибок линтера | Сумма `errorCount` из JSON-отчёта ESLint | При каждом запуске CI |
| 2 | Количество предупреждений линтера | Сумма `warningCount` из JSON-отчёта ESLint | При каждом запуске CI |
| 3 | Покрытие кода тестами | Доля покрытых строк по отчётам Vitest и JaCoCo | После запуска тестов |
| 4 | Количество пройденных и упавших тестов | Данные JUnit XML от Vitest и Maven Surefire | После запуска тестов |
| 5 | Частота коммитов | Количество коммитов в истории за последние 7 дней | При каждом запуске CI |
| 6 | Средний размер коммита | Среднее количество добавленных и удалённых строк на коммит за 7 дней | При каждом запуске CI |
| 7 | Время выполнения пайплайна | Разница между временем начала и временем сбора метрик в текущем запуске | В конце пайплайна |

Дополнительно скрипт считает непустые строки исходного кода. Эта величина используется для общего наблюдения за размером проекта, но не заменяет перечисленные выше метрики качества.

## 5. Проверка работы настроек

Для демонстрации работы системы контроля исходного кода необходимо выполнить следующие действия в GitHub:

1. Создать репозиторий и загрузить исходный код.
2. Убедиться, что workflow отображается во вкладке `Actions` и запускается при `push`.
3. Создать ветку `feature/demo-change`, внести небольшое изменение и отправить ветку в GitHub.
4. Создать Pull Request в `develop` и проверить результат commitlint и CI.
5. Убедиться, что обязательные проверки доступны в настройках защиты ветки.
6. Для проверки commitlint использовать корректное сообщение, например `docs(readme): update setup notes`; некорректный формат должен приводить к ошибке соответствующей проверки.
7. После успешного CI скачать артефакт `quality-metrics-*` и показать отчёт `metrics-report.md`.
8. После завершения учебного этапа создать тег версии и GitHub Release.

Для отчёта рекомендуется приложить скриншоты главной страницы репозитория, структуры каталогов, списка веток, успешного и неуспешного запусков workflow, настроек защиты веток, Pull Request, артефакта метрик и релиза.

В ходе лабораторной работы подготовлена структура GitHub-репозитория для проекта «Разработка web-приложения анализа цен на товары», определены правила оформления коммитов, стратегия ветвления, процесс слияния и порядок выпуска релиза.

Для автоматического контроля качества предусмотрены GitHub Actions, ESLint, модульные тесты frontend, интеграционный тест серверного HTTP-эндпоинта и отчёты покрытия Vitest/JaCoCo. Для завершения практической настройки необходимо загрузить файлы в собственный GitHub-репозиторий, включить правила защиты веток и выполнить первые запуски Actions. Фактические значения метрик и скриншоты добавляются в отчёт после выполнения этих действий.
